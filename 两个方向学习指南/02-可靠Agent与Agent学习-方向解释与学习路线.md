# 可靠 Agent 与 Agent 学习：方向解释与学习路线

更新日期：2026-10-27。你的第二优先方向。阅读目标：理解执行、验证和学习的差别，建立能检查成败的小环境。

## 1. 方向概述

**Agent 可以理解为：围绕目标，依据观察选择行动，并根据行动结果继续决策的系统。** 在 LLM Agent 中，大模型通常参与选择动作，但整个 Agent 还包括工具、运行程序、状态管理、记忆和评价机制。

“可靠 Agent”关注它是否稳定、正确地完成任务并满足约束；“Agent 学习”关注它如何利用数据、经验或反馈改善后续决策。

例如，一个数据分析 Agent 不只写出“分析完成”，还需要读取正确数据、运行计算、检查结果并生成要求的文件。可靠性要检查真实执行结果，不能只看最后一句回答是否流畅。

你已有工具检索和 RISA 反馈修复经历，适合从一个可验证的闭环进入。暂时不必把多 Agent、长期记忆和 RL 全部加进来。

## 2. Agent 是怎样工作的

```text
任务目标与约束
   ↓
观察当前状态 → 选择行动 → 调用工具 / 输出结果
   ↑                         ↓
更新记录和状态 ← 获得执行反馈并检查结果
   ↓
继续、修复、回退或终止
```

### 2.1 核心概念

| 概念 | 通俗解释 | 一个工具任务中的例子 |
| --- | --- | --- |
| Environment：环境 | Agent 作用的外部世界或模拟系统 | 数据库、文件系统、网页、游戏 |
| State：状态 | 环境在当前时刻的实际情况 | 某条记录当前是否已更新 |
| Observation：观察 | Agent 能看到的状态信息 | 查询接口返回的字段，可能不完整 |
| Action：动作 | Agent 选择执行的操作 | 查询、计算、更新、返回最终结果 |
| Tool：工具 | 可调用的能力及其输入输出规则 | 一个有类型和参数约束的函数 |
| Policy：策略 | 根据已有信息选择下一步的方式 | 模型、提示模板、规则共同决定调用 |
| Trajectory：轨迹 | 一次任务中观察、动作和结果的序列 | 每步调用、参数、返回值与验证结果 |
| Episode：任务回合 | 从开始到终止的一段完整交互 | 完成一次预约修改 |
| Horizon：时域长度 | 一个任务可能经历多少步 | 多步任务比单步任务更易累积错误 |
| Feedback：反馈 | 告诉系统结果如何的信息 | 参数非法、测试失败、缺少某字段 |
| Reward：奖励 | 学习或选择策略时使用的数值信号 | 成功得分、成本惩罚；设计需明确 |

状态和观察不同：数据库已经改变，Agent 可能因为接口超时没有看到结果。此时盲目重试写操作可能重复修改。要理解环境本身，不能把错误全部归因于模型“不会想”。

更形式化时，常用 MDP 描述状态、动作、转移和奖励；Agent 看不到完整状态时，可用 POMDP 的观点理解。不需要一开始推导完整理论，先能写出一个小环境的状态与转移即可。

### 2.2 大模型在其中承担什么

大模型可能负责理解目标、检索工具、选择参数、规划行动、解读反馈和输出结论。运行程序负责真正执行工具、维护状态和落实限制。

**Tool calling：** 模型生成结构化工具名与参数，程序检查并执行。生成了一段合法 JSON，不等于工具选对、参数正确或任务成功。

**ReAct：** 将推理与行动交替组织的一种方法，让外部观察影响后续选择。它是理解 Agent 闭环的经典入口，但不保证系统可靠，也不自动完成参数训练。[ReAct 原始论文](https://arxiv.org/abs/2210.03629)

**Workflow：** 预先规定较多步骤的流程。它与 Agent 没有绝对二分边界，实际系统经常混合固定流程与模型决策。学习重点是明确哪些步骤由谁决定、结果如何验证。

## 3. “可靠”具体包含什么

| 维度 | 应该问什么 | 可观察证据 |
| --- | --- | --- |
| 任务正确性 | 是否真正完成目标 | 最终环境状态、文件内容、执行结果 |
| 约束满足 | 是否保持必须不变的内容 | 禁止字段、非目标区域、预算检查 |
| 鲁棒性 | 输入变化、工具故障时能否工作 | 改写指令、缺失字段、超时等测试 |
| 稳定性 | 重复执行是否结果一致或可靠 | 重复运行的成功分布 |
| 错误恢复 | 能否发现失败、修复或回退 | 有效恢复比例、额外动作与副作用 |
| 校准与停止 | 是否知道证据不足、何时停止 | 不确定性与实际错误的关系 |
| 资源效率 | 成功需要多少调用与时间 | 完整费用、延迟、工具与模型调用数 |
| 可诊断性 | 能否定位失败原因 | 结构化日志、状态快照、错误分类 |

可靠性不是一个通用分数。例如视觉编辑中，异常是否完成与背景是否保持是两项要求；用一项很高的分数补偿另一项严重失败，可能不符合任务目标。评价前先定义必须满足的条件。

## 4. 为什么 Agent 会失败

以“查询数据、计算结果并写入文件”为例：

| 失败位置 | 典型表现 | 对应研究内容 |
| --- | --- | --- |
| 任务理解 | 漏掉时间范围或单位 | 指令理解、约束提取与任务表示 |
| 工具检索 | 召回的接口都不适用 | 工具表示、检索和重排 |
| 参数生成 | 日期、字段、实体或类型错误 | 结构化生成、校验、训练数据 |
| 计划与行动 | 步骤顺序错误或反复循环 | 规划、策略学习、计算预算 |
| 环境交互 | 超时、限流、返回结构变化 | 运行系统、重试、状态一致性 |
| 反馈解释 | 忽略报错，或相信错误 critic | 证据验证与反馈可靠性 |
| 记忆使用 | 复用旧版本经验，覆盖新证据 | 适用性、冲突、时效性与遗忘 |
| 终止与交付 | 没做完就声称成功，或不停尝试 | 完成检查、选择性停止与回退 |

先给失败分类，才能判断该改提示词、检索器、模型参数、评价器还是运行系统。增加模型规模未必解决环境故障；写更多重试逻辑也未必改善错误计划。

## 5. 这个方向具体包括哪些研究

### 5.1 执行验证：判断是否真的完成

**Verifier：验证器。** 检查候选行动、结果或最终任务是否满足要求。它可以是规则、测试、工具、模型或组合。

- 规则与类型检查：检查参数类型、范围、返回字段。
- 执行检查：实际运行代码或工具，检查最终状态。
- 证据检查：核对结论是否由检索内容或计算结果支持。
- 模型评估：对难以形式化的语义质量打分或诊断。
- 人工评价：用明确标准核查模型评价与真实需求的一致性。

验证器本身也会错。False positive 可理解为误判有缺陷，false negative 为漏掉缺陷；正式实验要明确定义“正类”。同一个模型既生成、又提出修复、又给最终分数，可能共享盲点，需有独立检查。

**Critic：评论或价值评估模块。** 有的给文字批评，有的预测动作价值；不是所有 critic 都是 RL 里的价值函数。

适合你的入口：RISA 中 VLM 的反馈是否与独立评价一致，哪些错误最容易漏检或误报。工具环境则先用可执行规则建立基准。

### 5.2 失败诊断、修复与停止

**Self-correction：自我纠错。** 根据反馈改进输出或行动。反馈可来自模型自身、外部工具或真实环境。

**Rollback：回退。** 返回先前更好的候选或环境状态。文件候选可保留版本；外部环境的操作未必可逆，因此要明确哪些动作可以回退。

**Selective repair：选择性修复。** 只在预期收益大于成本或风险时修复，或者只修改出错部分。阈值、规则或学习策略都可能实现。

应比较：单次执行、固定多轮修复、同预算独立重试、候选选择、阈值停止和回退。否则改进可能只是多花调用，而非反馈本身有用。

Self-Refine 研究任务内反馈修复；Reflexion 将反思文字保存用于后续尝试。理解这些经典机制之后，再判断自己的想法新增了什么。[Self-Refine](https://arxiv.org/abs/2303.17651)、[Reflexion](https://arxiv.org/abs/2303.11366)

### 5.3 记忆与经验迁移

| 概念 | 保存或改变什么 | 需要研究的问题 |
| --- | --- | --- |
| 工作上下文 | 当前任务中提供给模型的信息 | 容量有限，怎样保留必要证据 |
| Episodic memory | 过去任务或交互的记录 | 哪个案例相关，是否包含误导 |
| Semantic memory | 相对抽象的事实和知识 | 是否可信、过期、冲突 |
| Procedural memory / skills | 做事的方法、步骤或代码 | 前提是否满足、能否组合与迁移 |
| Reflection | 从轨迹中归纳的文字反思 | 是否正确归因，是否只适用一个案例 |

RAG 是检索外部信息并辅助生成的机制；记忆强调随交互保存和使用信息，两者可能共享检索技术。把聊天日志存进向量库，不等于已经解决长期记忆。

**经验迁移：** 从过去任务中获得的策略，能否改善未见任务。任务、工具版本、用户约束或模型改变后，旧经验可能失效。需要按任务族、时间或环境划分评测，不能把测试答案整理成“经验”再检索回来。

组内 Retrospex 将过去经验用于训练离线 critic 并影响行动选择；LifeBench 关注长期、多源记忆。它们分别代表不同研究切口。[Retrospex](https://aclanthology.org/2024.emnlp-main.268/)、[LifeBench](https://arxiv.org/abs/2603.03781)

### 5.4 Agent 学习：究竟学在哪里

并非每个学习系统都更新模型权重。阅读论文时先问：经验改变了哪个持久部分，后续任务是否使用它？

| 方式 | 核心操作 | 是否改变模型参数 | 怎样评价 |
| --- | --- | --- | --- |
| 当前上下文内适应 | 用当前反馈调整下一步 | 通常不改变 | 当前任务是否改善，增加多少成本 |
| 记忆与技能积累 | 保存经验、更新库或检索策略 | 未必改变底座 | 未见任务是否受益，有无错误积累 |
| Prompt / workflow 优化 | 根据数据改提示或流程 | 通常不改变底座 | 是否对保留任务和新模型泛化 |
| SFT | 用示范轨迹监督训练 | 改变训练参数 | 动作与完整任务成功是否提高 |
| 偏好优化 | 提高较好轨迹相对较差轨迹的概率 | 改变训练参数 | 偏好是否可靠、是否改善执行 |
| RL | 根据交互奖励优化策略 | 常见实现会改变策略参数 | 长期成功、成本和泛化 |

**SFT（监督微调）：** 给定上下文与示范动作，让模型学习生成正确行为。示范可来自专家、验证成功的轨迹或其他可靠来源；成功轨迹也可能包含多余或偶然动作，需要清理。

**LoRA：** 一种参数高效微调方式，在部分权重更新中使用低秩结构。它解决更新参数量与资源问题，并不自动保证训练更有效，也不是独立的 Agent 学习目标。

**DPO：** 用成对偏好数据训练模型更倾向被偏好的输出。它通常不需要显式训练奖励模型，也不意味着在环境中不断在线探索。轨迹偏好要与真实任务结果一致。[DPO](https://arxiv.org/abs/2305.18290)

### 5.5 RL 与训练信号

**RL：强化学习。** 策略执行行动、环境给反馈，学习过程让高回报行为更可能出现。在 LLM Agent 中，生成 token 与调用工具都可能影响后续轨迹。

基础概念包括：

- Return：累计回报，考虑一次任务中多个奖励。
- Value / Q：状态或状态—动作的预期后续回报。
- Advantage：某个行为相对参考基准有多好。
- Exploration：尝试不确定行动，寻找更好策略。
- Credit assignment：最终成败应归因于此前哪些行为。
- On-policy / off-policy：收集数据的策略与当前优化策略的关系。
- Offline RL：用固定交互数据学习，尤其要注意新策略选择数据中少见动作的风险。

**PPO：** 常见策略优化方法之一，通过约束更新幅度等机制改善训练稳定性；需要理解奖励、优势估计和相关实现。

**GRPO：** 利用同类输入的一组采样结果构造相对学习信号的一类方法。组内奖励的质量与差异性很重要；运行了 GRPO 并不证明模型学会了有用能力。

**Outcome reward：结果奖励。** 最终任务是否成功。真实但可能稀疏，难定位早期错误。

**Process reward：过程奖励。** 对中间步骤打分。信号更密，但容易引入评估器偏差。

**Reward hacking：奖励投机。** 模型找到提高评分、却没有真正完成目标的行为。应保留不参与训练奖励的独立检查，例如只奖励“测试通过”时还需确认测试本身未被错误修改。

推荐先理解并跑通 SFT，再判断是否需要 RL。RL 常包含轨迹生成、环境执行、奖励计算和训练，资源成本远不止一次反向传播。[TRL 官方文档](https://huggingface.co/docs/trl/index)、[verl 官方文档](https://verl.readthedocs.io/en/latest/)

### 5.6 数据、环境与评测也是研究内容

好的任务集需要清楚的输入、可观察信息、允许动作、成功条件与划分方式。任务模拟器也可能有错误或偏差，不能当作无条件真实世界。

τ²-Bench 用动态交互环境评测任务完成；LongMemEval 系列与 LifeBench 关注不同记忆能力。不同基准的成功分数不能直接互换。[τ²-Bench](https://arxiv.org/abs/2506.07982)、[LongMemEval 官方仓库](https://github.com/xiaowu0162/longmemeval)、[LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2)

构建新 benchmark 有可能形成贡献，但需要说明已有评价缺失了什么，并提供质量审核、基线和可复现协议。不能只因为创建了一批问题就认定有研究价值。

## 6. 怎样正确评价 Agent

| 指标 | 定义或用途 | 注意事项 |
| --- | --- | --- |
| Task success | 最终环境是否满足任务条件 | 由执行结果决定，不能仅凭自述 |
| Constraint satisfaction | 必须保持的要求是否满足 | 将硬约束与偏好分开 |
| Repair success | 初始错误中被修好的比例 | 分母是初始错误任务 |
| Regression rate | 初始正确中被改坏的比例 | 分母是初始正确任务，不能与上一项混用 |
| Tool validity | 工具名、类型、参数是否合法 | 合法不等于工具调用有用 |
| Repeatability | 同一任务重复执行的成功分布 | 报告任务数量与每任务运行次数 |
| Cost / latency | 完成任务的全流程消耗 | 包括失败、验证、记忆写入、重试和工具费用 |
| Generalization | 新任务、工具或环境中的效果 | 不在测试集上反复调提示与阈值 |

`pass@k` 常表示多次候选中至少一次成功的机会；它不等于能在未知真值时正确选出成功候选。某些工具基准另用 `pass^k` 表示多次都成功的稳定性指标，具体以官方协议为准，不能混写。

先用确定性环境检查基本能力，再逐步加入随机性和真实外部依赖。系统同时有多个随机来源时，保留逐样本轨迹、配对比较和重复运行；同一任务的重复采样不是多个独立任务。

## 7. 推荐学习路线与内容

这条路线作为第二优先时，主要先完成阶段 1–3。训练部分在兴趣、数据与资源明确后进入。

| 阶段 | 重点内容 | 动手练习 | 完成标准 |
| --- | --- | --- | --- |
| 1：理解闭环，约 1 周 | 状态、观察、动作、工具、轨迹与终止 | 用普通函数实现小环境，不急于引入框架 | 能逐步解释环境怎样改变 |
| 2：建立最小 Agent，1–2 周 | 工具 schema、调用解析、异常与步数限制 | 接一个可用模型，记录完整调用链 | 工具可执行，日志可检查，有明确成功检查 |
| 3：可靠性诊断，2–3 周 | 错误分类、反馈、重试、回退、停止 | 完成练习 A，比较固定修复与重试 | 有修好与改坏的统计、成本和失败例 |
| 4：经验与迁移，2–3 周 | 检索、记忆表示、适用性与划分 | 完成练习 B，不改变底座模型 | 在保留任务上检验收益和错误经验影响 |
| 5：监督学习，2–3 周或更长 | 轨迹数据、SFT、LoRA、偏好 | 若有资源，做练习 C 的小训练 | 不只训练损失下降，任务成功也经过验证 |
| 6：RL 基础与实现 | MDP、策略梯度、价值、优势、奖励与探索 | 先学简单 RL，再选择一个小型 Agent RL 任务 | 能解释奖励、采样、更新、成本和泛化 |
| 7：形成课题 | 定位一种失败机制，查最相近工作 | 写问题说明与完整验证计划 | 方法增益超过强基线，边界明确 |

| [LifeBench](https://arxiv.org/abs/2603.03781)、[LongMemEval-V2](https://arxiv.org/abs/2605.12493) | 阶段 4 | 多源记忆、长期经验与任务设置 |
| [DPO 原文](https://arxiv.org/abs/2305.18290)、[TRL](https://huggingface.co/docs/trl/index) | 阶段 5 | 偏好训练与训练数据格式 |
| [Hugging Face Deep RL Course](https://huggingface.co/learn/deep-rl-course/unit1/introduction) | 阶段 6 | 简单环境中的 RL 基础，之后再迁移到 LLM |
| [verl](https://verl.readthedocs.io/en/latest/) | 阶段 6，确有资源再用 | 轨迹生成、奖励和 LLM RL 训练系统 |
| [ImageRSI](https://arxiv.org/abs/2610.32120)、[MemCalib](https://arxiv.org/abs/2609.24259) | 确定相邻课题前 | 查修复、经验更新和记忆校准已有工作 |

阅读每篇论文都问：改了什么，训练或积累了什么，数据怎么分，谁给反馈，谁做最终评价，总预算多少，在哪些任务上无效。近期工作需继续查新，不能只把列表读完就认定找到了空白。

## 8. 三个练习项目

### 练习 A：一个可以检查成败的工具 Agent

用本地 JSON 或 SQLite 模拟库存/订单等简单数据，提供查询、计算和受限更新函数。定义几类任务，每类都能用最终状态写检查器，先在副本或模拟数据上执行。

先准备少量开发样本人工检查，然后扩展到约 30–50 个开发任务。保留未用于设计提示与阈值的新任务。比较单次执行、固定轮数修复、同预算独立重试和简单回退策略。

每步记录任务 ID、模型版本、观察、工具及参数、工具返回、错误、验证结果、费用与时间。不要只存模型最后的回答；不要要求读取不可获得的模型内部思维，外部动作和证据足以支持主要诊断。

产出：任务合同、完整日志、失败分类、修复成功与破坏比例、成本表。成功标准是评测可信，即使固定修复不如重试，也是一项有用观察。

### 练习 B：经验到底在帮忙还是添乱

在练习 A 的基础上，为成功/失败轨迹建立简洁经验库。比较无记忆、检索原轨迹、检索总结经验；保持上下文预算尽量一致。再改变一种环境条件，例如工具版本，观察经验能否适用。

必须明确：新版本信息能通过什么观察获得；经验库来自哪个数据划分；测试任务的答案没有进入经验。不要同时改变模型、工具、任务难度和记忆机制，否则难以解释结果。

产出：未见任务成功率、错误经验使用比例、额外读写成本，以及至少几例有益和有害迁移。若优势只是更多上下文造成的，应如实报告。

### 练习 C：从轨迹到一次小型学习实验

需具备训练资源和可靠数据。先整理正确动作或成功轨迹，按任务模板/族划分训练与测试，做小规模 SFT。对比同一个底座、不训练但使用示例、训练后的模型；说明额外训练和示例成本。

学习目标可以先限定为“正确选择工具与参数”，不急于训练整个长程策略。检查格式正确、动作正确、完整任务成功是否分别提高，并查看新工具或新任务上的泛化。

只有当示范难以覆盖、探索或长期回报确实重要时，再考虑 RL。先写出奖励如何计算、如何防止奖励投机、训练开销如何估算。不能仅因 RL 热门就添加训练环节。

## 9. 与你的已有项目怎样衔接

**RISA 入口：** 从已有修复轨迹中研究误报、漏报、过度修复和局部保持。原项目资源、数据权限与个人分工需要先确认。视觉任务的最终评价可结合掩码约束、独立模型与人工核查；单一像素指标或同一个 VLM 自评分不足以代表所有质量维度。

**金融工具入口：** 用固定数据快照与模拟 API 研究参数错误、版本变化、缓存过期和工具检索。先控制环境，再引入真实网络与时效性。

**与高效推理衔接：** 当模型调用成本可测后，比较应该把预算用于更多候选、一次更强推理、工具验证还是历史经验。先证明某项决策有实际收益，再考虑用训练策略替代规则。

## 10. 与 RSI 的关系及当前边界

反馈修复当前任务、为未来保存经验、更新策略参数、改进系统的改进机制，属于不同层次。它们都可与自我改进有关，但不能仅凭循环结构就证明较强意义的递归自我改进。

你当前最适合的目标是：让一个具体 Agent 在明确条件下更可靠，并用独立执行结果证明。以后若改进能持续保留、迁移到新任务，且改善后续改进过程，再进一步讨论 RSI。

能独立定义环境、检查成功、定位失败并做公平对照，就已有讨论课题的基础。下一步依据问题选择验证、记忆、SFT 或 RL；训练算法应服务于失败机制。
