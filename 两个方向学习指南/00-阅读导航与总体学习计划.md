# 两个研究方向：阅读导航与总体学习计划

更新日期：2026-10-27。面向：有 Python、机器学习及项目经历，希望逐步确定研究课题的研零学生。

你已选择先了解两个方向：第一优先是大模型高效推理，第二优先是可靠 Agent 与 Agent 学习。本套文件用于理解方向、学习基础和选择第一个实验，不预测四年后哪种岗位最热门。

| 文件 | 包含什么 | 建议阅读顺序 |
| --- | --- | --- |
| [01-大模型高效推理](01-大模型高效推理-方向解释与学习路线.md) | 生成过程、计算分配、缓存、量化、推测解码、服务调度、性能测量与分阶段练习 | 先读概述和概念，再按路线执行 |

## 2. 两个方向到底是什么关系

| 比较 | 大模型高效推理 | 可靠 Agent 与 Agent 学习 |
| --- | --- | --- |
| 关注的对象 | 模型生成与模型服务的计算过程 | 模型、工具和环境组成的任务执行过程 |
| 典型问题 | 为什么慢、为什么占显存、哪些计算可以省 | 为什么任务失败、反馈是否可信、经验能否迁移 |
| 主要观察 | token、注意力、缓存、算子、调度 | 状态、动作、观察、轨迹、反馈、奖励 |
| 典型评价 | 质量、延迟、吞吐、显存、成本 | 任务成功、约束满足、稳定性、成本、泛化 |
| 常见产出 | 压缩或解码算法、计算策略、推理系统 | 验证方法、决策策略、数据与训练方法、评测环境 |

一个 Agent 每次调用模型都要付出推理成本；一个高效模型也可能在任务中反复调用错误工具。两者可以互相支撑，但“模型 tokens/s 更高”不能直接证明“Agent 更可靠”，任务成功率提高也不能自动证明底层推理更快。

可以把未来的交叉问题写成：**在相同任务预算下，怎样让 Agent 把计算用在最有价值的推理、验证和行动上？** 初期先学清两侧概念，不要同时优化整个系统。

## 3. 适合你的起点

结合本轮已读取的材料：STARS 可帮助你进入循环推理、稳定性和计算分配；RISA 可帮助你理解反馈、修复和多目标约束；金融 API 项目可帮助你理解工具检索与执行错误。项目参与不等于已经独立掌握所有模块，先做能力盘点。

| 自查问题 | 若能独立完成 | 若暂时不能 |
| --- | --- | --- |
| 从 token 输入追踪 Transformer 一次前向的主要张量形状 | 加快效率指南阶段 1 | 先补注意力、张量运算与自动微分 |
| 复现一个检查点在固定数据上的结果 | 开始测性能与分析失败 | 先学配置、数据处理和评测脚本 |
| 为工具任务写出明确的成功检查器 | 开始做 Agent 基线 | 先缩小任务，建立可执行真值 |
| 解释一次提升是否来自更多预算 | 开始做方法比较 | 先补强基线与公平实验 |

## 4. 前 12 周怎么分配

以下按每周 12–16 小时估计：约 8–10 小时用于主方向，3–4 小时用于 Agent，剩余时间整理记录。时间不足时延长周期；表格中的产出比日期重要。两份分方向路线是能力阶段，不要求在 12 周里全部学完。

| 周次 | 高效推理主线 | Agent 辅线 | 本周交付物 |
| --- | --- | --- | --- |
| 1–2 | Transformer、自回归生成、prefill/decode；跑通小模型 | 明确状态、动作、工具与终止条件 | 一张生成流程图；一个小任务的输入输出合同 |
| 3–4 | KV cache 原理、显存估算；建立质量与性能基线 | 写最小 Agent 循环与执行检查器 | 一份可信基线；逐条可检查的 Agent 日志 |
| 5–6 | profiler、输入输出长度对瓶颈的影响 | 固定修复、重试、回退的对照 | 性能瓶颈报告；至少 20 条失败分析 |
| 7–8 | 选一个小实验：缓存、量化或循环深度 | 比较反馈是否真的改善执行结果 | 一个变量的对照图；错误修复与破坏比例 |
| 9–10 | 针对实验读 2–3 篇直接相关论文 | 了解记忆、SFT 与 RL 的差别 | 相关工作差异表；一个可推翻假设 |
| 11–12 | 在新任务或负载下复核，决定继续哪条分支 | 根据需要补泛化或训练实验设计 | 两页选题说明、可运行入口和资源需求 |

前 12 周不要求掌握 CUDA、分布式 RL 或完成论文。目标是形成一次完整的“问题—基线—诊断—干预—验证”过程。

## 5. 每周应该留下什么

每周只安排一个主要问题，例如“长输入主要增加哪一部分时间”。保留：

- 一页学习笔记：用自己的话解释概念，附一个例子。
- 一份运行记录：模型、数据版本、配置、机器、结果和失败信息。
- 一项观察：支持或否定了什么假设，哪些仍不知道。
- 一个下周动作：最小、明确、能检验当前不确定性。

建议在以后实际开展实验时建立这样的目录，本次只提供结构说明：

```text
research_project/
  README.md          # 问题、运行方法、主要结论
  configs/           # 可复用配置
  src/               # 实现与评测
  runs/              # 原始输出、轨迹与时间记录
  analysis/          # 图表和逐样本分析
  notes/             # 论文卡与实验日志
```

不要只保存最终分数。性能研究需要原始测量，Agent 研究需要完整轨迹；错误和负结果也有诊断价值。

## 6. 环境与资源怎么安排

先确认已有资源，再选择任务规模。本指南不据简历推定你拥有某种 GPU。

| 资源 | 可先完成的工作 | 暂缓的工作 |
| --- | --- | --- |
| CPU、无付费 API | 概念学习、小型注意力实现、模拟工具、确定性检查器 | 有代表性的 GPU 性能结论、大模型训练 |
| 有少量 API 预算 | Agent 原型、轨迹诊断、不同反馈策略 | 模型内部隐状态与内核研究；API 延迟不能代替纯计算时间 |
| 单张 GPU | 选择能容纳的小模型做性能与质量对照 | 未测资源就安排长上下文、多模型和 RL 训练 |
| 稳定组内服务器与指导 | 检查点分析、轻量训练、服务调度；资源足够后再扩大 | 不应以“有卡”为理由跳过基线和评价 |

可使用 Windows 做阅读、编辑和小型脚本；性能或训练实验按框架支持情况选择 Linux 服务器等环境。不要为了教程随意改动现有 Windows/WSL 环境。真正安装前，先确定系统、GPU、驱动、框架版本和可回退方案。

## 7. 如何选第一个实验

首选“高效推理指南中的练习 A：生成性能基线”。如果 STARS 资源可得，再做练习 D 的循环深度诊断。Agent 辅线选择“工具任务的修复与重试对照”。

两周后检查：你能否自己解释结果？能否复现？遇到失败时是否愿意继续查？这些信息比仅凭论文标题判断兴趣更有用。

如果训练资源无法持续获得，仍可先完成模拟 Agent 和小模型分析；如果系统测量令你明显更感兴趣，就继续深入缓存与服务；如果你更喜欢研究决策错误与学习反馈，再调整主辅比例。

## 8. 四年尺度上应积累的东西

目前只详细规划前 12 周。之后按实际结果调整：先获得独立复现实验的能力，再独立负责一个窄问题，随后通过论文或实习验证兴趣，最后决定偏算法研究、系统研发还是 Agent 学习。

较长久的基础包括概率统计、优化、算法、系统原理、严谨实验和清晰表达。具体模型、框架和热门课题会变化；阶段目标是让这些基础通过真实工作逐渐变扎实。

本套指南延续此前对组内研究的梳理，并核对当前相关官方资料；对个人经历的判断依赖本次对话提供的材料，未额外审计项目分工或实验数字。更详细的方向取舍见上一级的[研究方向建议与上手路线](../研究方向建议与上手路线-2026-10-27.md)。
